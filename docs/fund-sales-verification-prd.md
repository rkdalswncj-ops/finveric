## 서비스 정의

서비스명은 **핀베릭(FINVERIC)**이다. 프로젝트 폴더와 저장소 이름은 `finveric`이다.

**펀드 판매 과정의 조건 충족과 처리 이력을 자산운용사·판매 증권사·고객·검증자가 함께 확인하는 B2B 플랫폼이다.**

고객은 판매 증권사의 화면에서 펀드를 고르고 가입 절차를 진행한다. 플랫폼은 진단, 재진단, 설명 확인, 서명을 같은 판매 건으로 연결한다. ZKP는 고정한 답변이 지정한 규칙을 충족했는지 증명한다. 스마트컨트랙트는 증명과 필수 기록을 확인하고 다음 상태로의 전환을 통제한다. 고객은 받은 증빙을 원장과 별도로 대조할 수 있다.

해결할 핵심 문제는 분쟁 당사자인 판매사에 판매 기록과 검증 경로가 집중된다는 점이다. 운용사와 증권사의 연결은 공동 검증을 지원하는 구조다. 거래 전달 속도나 판매량 증대를 제품의 첫 검증 목표로 삼지 않는다. [Notion 기획 원문: 투자상품 판매 과정 기록 원장](https://example.invalid)

## 참여자와 책임

| 참여자 | 책임과 화면 |

| 투자자 | 상품을 확인하고 진단에 답한다. 설명과 답변을 확인하고 모의 서명한다. 증빙을 내려받아 본인 기록을 검증한다. |
| 외부 검증자 | 지정된 네트워크·컨트랙트를 기준으로 상태, 버전, 증명, 이벤트를 별도로 대조한다. 감독기관의 공식 참여를 뜻하지 않는다. |
| 기존 펀드 업무 인프라 | 매입 요청, 자금 처리, 기준가격·좌수 등 거래 결과를 처리한다. MVP는 모의 연동을 쓴다. |

운용사의 상품 등록과 판매사의 고객 적합성 판단을 같은 권한으로 취급하지 않는다. 실제 판매·보관·감독 책임을 컨트랙트에 이전한다고 가정하지 않는다.

## 기존 인프라와 블록체인의 역할

한국예탁결제원은 펀드넷을 통한 집합투자증권과 집합투자재산 관리 서비스를 제공한다. 우리 서비스는 기존 공동 인프라의 존재를 전제로 설계한다. 이번 MVP는 펀드넷을 대체하거나 실제로 연동하지 않는다. [한국예탁결제원 서비스 안내](https://www.ksd.or.kr/ko/)

블록체인은 판매사 결과 화면과 별도로 조회할 수 있는 공동 검증 기준을 제공한다. 각 역할이 제출한 기록의 순서와 상태 전환을 확인한다. 스마트컨트랙트는 등록한 규칙과 증빙을 검사한다. 실제 매입을 통제하려면 기존 주문 시스템도 그 결과를 필수 조건으로 확인해야 한다.

참여 기관이 동일한 중앙 운영자를 충분히 신뢰한다면 공통 DB와 전자서명으로 처리할 수도 있다. 블록체인의 추가 가치는 독립 검증, 공동 변경 통제, 분쟁 근거 확인에 드는 비용으로 평가한다. 한 사업자가 모든 서명 키와 변경 권한을 독점하면 이점이 줄어든다. 실제 운영망과 접근 권한은 도입 기관과 합의해야 한다.

ZKP는 비공개 답변에 대한 계산 결과를 검증한다. 원문이나 총점을 공개하지 않는다. 최초 입력의 사실성, 고객의 실제 이해, 실제 서명자의 신원을 자동으로 증명하지는 않는다. 해시와 증명은 원본 보관을 대체하지 않는다. [Ethereum 스마트컨트랙트](https://ethereum.org/developers/docs/smart-contracts/) · [ZKP 안내](https://ethereum.org/zero-knowledge-proofs/)

## 핵심 기능

1. **상품·규칙 버전 관리.** 운용사는 상품과 설명서를 등록한다. 판매사는 진단 규칙을 등록한다. 같은 판매 건이 참조한 버전과 적용 이력을 남긴다.
2. **진단과 재진단 기록.** 고객이 확인한 답변을 회차별로 고정한다. 기존 회차를 덮어쓰지 않는다. 재진단 횟수와 결과를 담당자에게 보여준다.
3. **ZKP 조건 검증.** 선택지 범위, 배점, 합계, 위험 확인 조건을 회로로 계산한다. 합격·불합격 결과 모두 증명해 이력에 남긴다.
4. **가입 단계 통제.** 유효한 최종 진단, 설명서 확인, 모의 서명, 필요한 추가 검토가 있어야 가입 조건 검증을 완료한다.
5. **고객용 증빙과 독립 검증.** 고객이 받은 가상 원본과 검증 영수증을 내보낸다. 판매사 API 없이 원장 기록과 대조한다.
6. **기관별 업무 화면.** 운용사는 상품 버전을 관리한다. 판매사와 준법 담당자는 가입 건과 예외를 본다. 외부 검증자는 같은 판매 ID로 근거를 조회한다.
7. **원본 보관 연동.** 제품 운영안은 별도 보관 서비스, 암호화, 접근 권한, 보존 기간을 포함한다. 기말 MVP는 고객 다운로드로 범위를 한정한다.

## BM

첫 구매자는 판매 증권사의 소비자보호·준법·디지털채널 조직으로 가정한다. 운용사의 판매지원 조직도 구매자 후보다. 여러 판매사에 같은 상품 문서와 버전을 전달하는 기능에 비용을 지불할 수 있는지 확인한다. 감독기관은 검증 참여자로 가정하며 첫 매출의 전제에 두지 않는다.

| 수익원 | 제공하는 것 | 과금 기준 가설 |
| --- | --- | --- |
| 초기 연동 비용 | 기존 가입 화면·주문 API 연결, 역할 설정, 진단 규칙 구현 | 기관과 연동 시스템 범위 |
| 기관별 연간 사용료 | 판매절차 검증 API, 기관별 화면, 이력 조회, 운영 지원 | 기관 단위 계약과 포함 처리량 |
| 추가 모듈 비용 | 추가 상품군·채널·운용사 연결, 증빙 보관 연동, 규칙 유지보수 | 모듈과 지원 범위 |

첫 계약은 한 펀드·한 온라인 판매 채널의 유료 파일럿으로 가정한다. 투자자 한 명의 증거 수집 시간, 추가 원본 요청 건수, 적용 기준 대조 시간, 예외 처리 시간을 기존 방식과 비교한다. 규칙 구현·회로 변경·지원 비용도 측정한다. 정확한 가격, 지불 의향, 비용 절감률은 미검증이다. 법적 책임이나 배상액 감소를 보장하는 상품으로 판매하지 않는다.

## 기말 MVP 범위

- 가상 개방형 공모펀드 한 종과 가상 온라인 클래스 하나를 쓴다.
- 운용사 한 곳, 판매 증권사 한 곳, 가상 고객 한 명, 판매사 준법 담당자, 외부 검증자 역할을 시연한다.
- 운용사·판매사·준법 담당자·모의 거래 연동 주체는 별도 테스트 키를 쓴다. 고객 확인도 모의 키로 시연한다.
- 상품 문서 v1과 진단 규칙 v1을 쓴다. 원본 파일 변경과 등록하지 않은 버전 사용은 별도 공격 시나리오로 확인한다.
- 진단 세 회차를 한 판매 세션에 연결한다. 고객이 새 계정이나 다른 판매사로 재시도하는 경우의 통합 추적은 제외한다.
- 실제 ZKP 생성·검증과 Sepolia 거래를 연결한다. 본인인증·전자서명·자금·펀드 매입 결과는 모의 처리로 표시한다.
- 가입 조건 검증 뒤 모의 매입 결과를 반영한다. 환매·만기·자금 결제·수익증권 토큰 발행·DEX는 이번 범위에서 제외한다.
- 가상 원본의 고객 다운로드와 독립 검증을 포함한다. 공인전자문서센터·상용 보관소 연동은 제외한다.
- Vercel 웹 하나에 사용자와 관리자 사이드 탭을 둔다. 관리자 안에서 운용사·증권사·검증자 역할을 전환한다. 별도 모바일 앱은 만들지 않는다.

펀드 가입은 판매회사를 통해 진행할 수 있다. 매입 좌수는 적용 기준가격과 금액으로 계산한다. 구체적인 적용일과 수수료는 펀드별 문서를 따라야 한다. 아래 수치는 시연용 가정이다. [삼성자산운용 투자 프로세스](https://www.samsungfund.com/fund/insight/guide/view08.do)

### 시연 규칙 v1

| 문항 | 0점 | 1점 | 2점 |
| --- | --- | --- | --- |
| 손실 감내 | 손실 감내 어려움 | 일부 손실 감내 가능 | 큰 손실도 감내 가능 |
| 투자 경험 | 경험 없음 | 펀드 투자 경험 있음 | 여러 위험자산 투자 경험 있음 |

합계 3점 이상이고 위험 확인 문항에 통과하면 시연의 진단 조건을 충족한다. 선택지와 위험 확인 값은 허용 범위여야 한다. 이 규칙은 실제 공모펀드의 적합성 판정표나 법적 가입 자격을 재현하지 않는다.

두 번째 진단부터 재진단 표시를 붙인다. 세 번째 진단을 진행하면 추가 검토가 필요하다. 준법 담당자의 검토는 유효한 최종 진단·설명 확인·모의 서명을 대신하지 않는다. 미충족 회차도 유효한 결과 증명으로 기록한다. 실패한 증명을 무시해 회차가 사라지지 않게 한다.

시연의 반복 진단은 문제 상황을 재현하는 가상 데이터다. 고객 화면에서 기준 통과를 목적으로 재진단을 권유하지 않는다. 고객이 답변 정정을 요청하면 이전 회차를 보존하고 새 회차로 기록한다.

### 상태와 데이터

판매 절차 상태는 `진행 중 / 추가 검토 필요 / 가입 조건 검증 완료`로 구분한다. 매입 상태는 `미요청 / 요청 접수 / 결과 대기 / 매입 결과 반영(모의)`으로 별도 표시한다. 거래 영수증이 없으면 온체인 단계는 대기 상태다. 조건 검증 완료를 실제 매입 완료로 표시하지 않는다.

각 판매 ID는 상품·클래스·판매사·가상 고객 세션에 연결한다. 진단 회차는 순서대로 증가한다. 모의 고객 확인 키가 회차별 답변 커밋먼트를 먼저 고정한다. 증명은 같은 커밋먼트와 규칙 버전, 원장 도메인, 판매 ID, 진단 회차에 연결한다. 원장 도메인은 네트워크와 컨트랙트를 구분한다. 모의 서명은 같은 판매 ID, 최종 진단 회차, 답변 커밋먼트, 설명서 버전에 연결한다.

회로는 비공개 답변으로 점수와 통과 여부를 계산한다. 검증 가능한 공개 결과는 통과 여부다. 따라서 미충족 답변도 `통과=false`인 유효한 증명을 생성할 수 있다. 컨트랙트는 이력을 남기되, 해당 결과로 가입 조건 검증을 완료하지 않는다. 증명 자체가 유효하지 않은 요청은 거절한다.

Sepolia에는 가상 기관·상품 식별자, 무작위 판매 ID, 커밋먼트, 진단 회차, 통과 여부, 확인 기록, 증명, 거래 이력이 공개될 수 있다. 답변·총점·비공개 임의값·실제 개인정보는 올리지 않는다. 증명 생성 서버는 가상 답변을 볼 수 있다. 실제 서비스의 정보 공개 범위와 네트워크는 별도로 결정한다.

고객 다운로드는 두 파일로 나눈다. 검증 영수증에는 판매·상품·버전 식별자, 커밋먼트, 네트워크·컨트랙트 주소, 거래 참조를 넣는다. 고객용 원본 묶음에는 가상 답변·임의값·확인한 문서·모의 서명을 넣는다. 원본 묶음을 공개 원장이나 공유 링크에 올리지 않는다. 검증 화면은 파일이 가리킨 임의의 원장을 신뢰하지 않고, 미리 설정한 네트워크와 주소를 사용한다.

## 기말 시연 시나리오

목표 시연 시간은 약 6~8분이다. 테스트넷 대기 시간은 별도다. 시간은 실제 리허설로 확인한다.

| 순서 | 발표자의 동작 | 확인할 결과 |
| --- | --- | --- |
| 1. 상품과 기준 | 운용사 화면에서 가상 펀드 A와 문서 v1을 등록한다. 판매사 규칙 v1도 연결한다. | 고객 카드에서 누가 운용하고 누가 판매하는지 확인한다. |
| 2. 진단 이력 | 고객이 105만원 가입을 시작한다. 세 회차의 점수 합계는 1점, 2점, 3점이다. 위험 확인은 통과한다. | 앞의 두 회차는 미충족으로 남는다. 세 번째 회차는 충족이지만 추가 검토가 필요하다. 점수는 고객용 가상 원본에만 있다. |
| 3. 단계 누락 거절 | 처리 화면에서 필수 모의 서명 확인이 빠진 완료 요청을 제출한다. | 컨트랙트가 거절한다. 거래 실패를 표시하고 절차 상태를 유지한다. |
| 4. 정상 검증 완료 | 고객이 핵심 설명·답변·문서를 확인하고 모의 서명한다. 준법 담당자가 재진단 이력을 검토하고 승인한다. | 실제 ZKP와 필수 기록을 확인한 뒤 가입 조건 검증 완료를 기록한다. 고객이 영수증과 가상 원본을 내려받는다. |
| 5. 모의 매입 결과 | 모의 거래 연동이 105만원, 기준가격 1,050원(1,000좌당), 매입 시 공제 비용 0원을 전달한다. | 매입 결과를 100만좌로 표시한다. 가격·좌수·자금은 모의 처리라고 표시한다. |
| 6. 사후 변경 시도 | 판매사 보관용 가상 답변 또는 설명서 사본을 바꾼다. 원장 기록 변경과 다른 판매 ID의 증명 재사용도 시도한다. | 원본 대조가 불일치를 표시한다. 고정된 회차의 덮어쓰기와 증명 재사용은 거절한다. |
| 7. 독립 검증 | 판매사 조회 API를 사용하지 않는 검증 화면에서 고객의 기존 파일을 연다. | RPC로 같은 판매 ID와 버전·증명·이력을 확인한다. 고객이 가진 원본은 검증되고, 수정한 사본은 불일치한다. |

매입 좌수 계산은 `1,050,000원 ÷ 1,050원 × 1,000좌 = 1,000,000좌`다. 기준가격 적용 시점은 모의 거래 결과의 필드로 표시한다. 블록체인 시각을 실제 펀드 기준가격 적용일로 대신하지 않는다.

사후 변경 시나리오는 탐지와 덮어쓰기 거절을 보여준다. 판매사의 원본 삭제를 원장만으로 복구한다고 설명하지 않는다. 고객의 원본도 없으면 해시만으로 내용을 복구할 수 없다. 별도 기관의 원본 보관과 장기 접근 보장은 후속 구현이다.

## 완료 기준

| 상황 | 기대 결과 |
| --- | --- |
| 세 회차의 진단 | 회차 1·2·3과 결과 false·false·true가 유지된다. 마지막 결과로 이전 이력을 덮어쓰지 않는다. |
| 답변 바꿔치기·다른 회차·다른 판매 ID·다른 원장에서 증명 재사용 | 공개 입력과 등록값을 대조해 거절한다. |
| 규칙 밖 선택지 | 유효한 증명을 생성할 수 없다. |
| 모의 서명·설명 확인·추가 검토 누락 | 조건 검증 완료를 거절한다. |
| 추가 검토 승인만 있고 진단 미충족 | 완료를 거절한다. 승인이 계산 결과를 우회하지 않는다. |
| 등록하지 않은 설명서·규칙 버전 | 해당 요청을 거절한다. |
| 중복 완료·중복 모의 매입 결과 | 같은 판매 건에 중복 반영하지 않는다. |
| 거래 영수증 대기·실패 | 완료 상태로 표시하지 않는다. 실패 이유와 현재 상태를 구분한다. |
| 고객 원본과 변경한 사본 | 원래 파일은 대조에 통과한다. 변경한 사본은 불일치를 표시한다. |
| 독립 조회 | 판매사 API 없이 지정 RPC·컨트랙트로 기록을 확인한다. |
| 공개 데이터·로그 검사 | 답변·총점·임의값·실제 개인정보·서명 키가 없다. 통과 여부 공개는 화면과 문서에 명시한다. |
| 모의 매입 | 105만원과 1,000좌당 1,050원으로 100만좌를 표시한다. 실제 자금 이동과 구분한다. |

## 구현 순서와 현재 상태

1. 회로에서 통과·미충족 결과를 모두 증명한다. 허용 범위를 벗어난 입력과 커밋먼트 불일치를 검사한다.
2. Foundry에서 버전 등록, 회차 고정, 단계 통제, 추가 검토, 완료 기록, 모의 매입 결과를 검증한다.
3. 고객 파일 내보내기와 판매사 API를 쓰지 않는 RPC 검증을 연결한다.
4. 기존 화면 스타일로 상품 탐색·가입·기관 업무·처리 로그를 구현한다.
5. Vercel 웹, Render API, Sepolia로 외부 접속을 확인한다. Anvil로도 같은 코드를 리허설한다.

현재 산출물은 기획 문서와 [클릭형 펀드 HTML 시안](fund-ui-prototype.html)이다. 시안은 전체 모의 처리다. 실제 ZKP·Sepolia·API를 연결한 펀드 MVP는 구현 전이다. 기존 ZKP 실험 결과가 새 회로와 배포 환경의 검증을 대신하지 않는다. 개발 스택은 README를 따른다. 기존 ELS 공동 청약 설계는 [보관 문서](archive/2026-11-08-els-shared-subscription-prd.md)에 남긴다.
