## 서비스 정의

서비스명은 **핀베릭(FINVERIC)**이다. 프로젝트 폴더와 저장소 이름은 `finveric`이다.

**펀드 판매 과정의 조건 충족과 처리 이력을 자산운용사·판매 증권사·검증자가 함께 확인하는 B2B·B2G 플랫폼이다.**

FINVERIC 화면의 사용자는 기관이다. 운용사·증권사·준법 담당자는 client 앱을 쓴다. 감독기관·외부 검증자는 auditor 앱을 쓴다. 투자자는 FINVERIC 화면을 직접 쓰지 않는다. 고객은 판매 증권사의 화면에서 펀드를 직접 고르고 가입 절차를 진행한다. 증권사 화면이 FINVERIC API에 연결한다. 플랫폼은 투자성향 진단, 설명 확인, 추가 위험 확인을 같은 가입 건으로 연결한다. ZKP는 고정한 답변에서 등록된 규칙에 따라 투자성향을 계산했음을 증명한다. 고객이 최종 확인하면 스마트컨트랙트가 증명과 필수 동의를 검사하고 한 거래에서 가입을 확정한다. 고객은 받은 증빙을 원장과 별도로 대조할 수 있다.

해결할 핵심 문제는 분쟁 당사자인 판매사에 판매 기록과 검증 경로가 집중된다는 점이다. 운용사와 증권사의 연결은 공동 검증을 지원하는 구조다. 거래 전달 속도나 판매량 증대를 제품의 첫 검증 목표로 삼지 않는다.

## 문제와 검증할 가치

| 문제 | 제공할 기능 | 검증할 가치 |
| --- | --- | --- |
| 가입 후 답변이나 판정 기록을 바꾸면 원래 기록과 구분하기 어렵다. | 고객 확인 시점의 답변 커밋먼트와 판정 규칙 버전을 고정한다. 수정은 새 회차로 남긴다. | 원래 기록과 변경 이력을 함께 확인한다. |
| 재진단을 반복해도 마지막 결과만 보일 수 있다. | 같은 임시 가입 건에서 진단 회차를 이어가고 최종 거래에 포함한다. | 담당자가 반복 진단을 보고 검토한다. |
| 어떤 설명서와 기준을 적용했는지 다시 모아야 한다. | 운용사의 상품·설명서 버전과 판매사의 진단·판정 규칙 버전을 구분한다. | 판매 당시 적용한 기준을 대조한다. |
| 필수 확인이 빠진 채 다음 처리로 넘어갈 수 있다. | 증명, 설명서 확인, 거래 송신자와 필요한 추가 위험 확인·준법 검토를 검사한다. | 연결된 가입 경로에서 단계 누락을 거절한다. |
| 고객이 판매사가 제공하는 사본과 결과 화면에 의존한다. | 고객용 증빙 파일과 독립 검증 화면을 제공한다. | 판매사 API 없이 받은 기록을 원장과 대조한다. |
| 판매사가 원본을 잃거나 삭제하면 원장 해시만으로 복구할 수 없다. | 제품 운영안은 독립 보관 연동과 고객의 원본 접근 수단을 포함한다. MVP는 고객이 내려받은 가상 원본으로 검증한다. | 변경 탐지와 원본 보존을 구분해 확인한다. |

문제 유형은 Notion 기획을 계승한다. 현재 발생 빈도, 처리 비용, 구매 의향은 아직 검증하지 않았다. 파일럿과 담당자 인터뷰로 확인한다.

| 감독기관·외부 검증자 (B2G) | 지정된 네트워크·컨트랙트를 기준으로 상태, 버전, 증명, 이벤트를 별도로 대조한다. 감독기관의 공식 참여를 가정하지 않는다. | auditor 앱 |
| 투자자 | 상품을 확인하고 진단에 답한다. 설명과 답변을 확인하고 가입을 요청한다. 증빙을 내려받아 본인 기록을 확인한다. | 증권사 앱. FINVERIC 화면은 쓰지 않는다. 시연은 client 앱의 판매 채널 시연으로 보여준다. |
| 기존 펀드 업무 인프라 | 매입 요청, 자금 처리, 기준가격·좌수 등 거래 결과를 처리한다. MVP는 모의 연동을 쓴다. | 없음 |

운용사의 상품 등록과 판매사의 고객 적합성 판단을 같은 권한으로 취급하지 않는다. 실제 판매·보관·감독 책임을 컨트랙트에 이전한다고 가정하지 않는다.

## 기존 인프라와 블록체인의 역할

한국예탁결제원은 펀드넷을 통한 집합투자증권과 집합투자재산 관리 서비스를 제공한다. 우리 서비스는 기존 공동 인프라의 존재를 전제로 설계한다. 이번 MVP는 펀드넷을 대체하거나 실제로 연동하지 않는다. [한국예탁결제원 서비스 안내](https://www.ksd.or.kr/ko/)

블록체인은 판매사 결과 화면과 별도로 조회할 수 있는 공동 검증 기준을 제공한다. 각 역할이 제출한 기록의 순서와 상태 전환을 확인한다. 스마트컨트랙트는 등록한 규칙과 증빙을 검사한다. 실제 매입을 통제하려면 기존 주문 시스템도 그 결과를 필수 조건으로 확인해야 한다.

참여 기관이 동일한 중앙 운영자를 충분히 신뢰한다면 공통 DB와 전자서명으로 처리할 수도 있다. 블록체인의 추가 가치는 독립 검증, 공동 변경 통제, 분쟁 근거 확인에 드는 비용으로 평가한다. 한 사업자가 모든 서명 키와 변경 권한을 독점하면 이점이 줄어든다. 실제 운영망과 접근 권한은 도입 기관과 합의해야 한다.

ZKP는 비공개 답변에 대한 계산 결과를 검증한다. 원문과 총점은 원장에 직접 기록하지 않는다. 공개된 투자성향이 균형형이면 총점이 2점임을 알 수 있다. 최초 입력의 사실성, 고객의 실제 이해, 실제 서명자의 신원은 별도 근거가 필요하다. 해시와 증명은 원본 보관을 대체하지 않는다. [Ethereum 스마트컨트랙트](https://ethereum.org/developers/docs/smart-contracts/) · [ZKP 안내](https://ethereum.org/zero-knowledge-proofs/)

## 핵심 기능

1. **상품·규칙 버전 관리.** 운용사는 상품과 설명서를 등록한다. 판매사는 진단 규칙을 등록한다. 같은 판매 건이 참조한 버전과 적용 이력을 남긴다.
2. **진단과 재진단 기록.** 가입 중에는 답변과 증명을 임시로 보관한다. 답변을 정정하면 같은 가입 건에 다음 회차를 추가한다. 고객이 가입을 중단하면 임시 기록을 폐기한다.
3. **ZKP 투자성향 검증.** 회로는 선택지 범위와 점수 합계를 확인하고 투자성향을 계산한다. 최종 거래에서 컨트랙트가 각 회차의 증명을 검증한다.
4. **가입 단계 통제.** 고객은 상품 설명을 확인한다. 직접 고른 상품이 투자성향보다 위험하면 추가 안내와 직접 청약 의사를 확인한다. 세 번째 진단부터는 준법 검토도 필요하다. 필수 조건이 갖춰지면 테스트 고객 계정이 가입 거래를 한 번 제출한다.
5. **고객용 증빙과 독립 검증.** 가상 원본과 검증 영수증을 내려받을 수 있다. 가입 이력에서 선택한 건이나 보관한 파일을 원장 기록과 대조한다.
6. **기관별 업무 화면.** 운용사는 상품 버전을 관리한다. 판매사와 준법 담당자는 가입 건과 예외를 본다. 외부 검증자는 같은 판매 ID로 근거를 조회한다.
7. **원본 보관 연동.** 제품 운영안은 별도 보관 서비스, 암호화, 접근 권한, 보존 기간을 포함한다. 기말 MVP는 고객 다운로드로 범위를 한정한다.

## BM

첫 구매자는 판매 증권사의 소비자보호·준법·디지털채널 조직으로 가정한다. 운용사의 판매지원 조직도 구매자 후보다. 여러 판매사에 같은 상품 문서와 버전을 전달하는 기능에 비용을 지불할 수 있는지 확인한다. 감독기관은 검증 참여자로 가정하며 첫 매출의 전제에 두지 않는다.

| 수익원 | 제공하는 것 | 과금 기준 가설 |
| --- | --- | --- |
| 초기 연동 비용 | 기존 가입 화면·주문 API 연결, 역할 설정, 진단 규칙 구현 | 기관과 연동 시스템 범위 |
| 기관별 연간 사용료 | 판매절차 검증 API, 기관별 화면, 이력 조회, 운영 지원 | 기관 단위 계약과 포함 처리량 |
| 추가 모듈 비용 | 추가 상품군·채널·운용사 연결, 증빙 보관 연동, 규칙 유지보수 | 모듈과 지원 범위 |

첫 계약은 한 펀드·한 온라인 판매 채널의 유료 파일럿으로 가정한다. 투자자 한 명의 증거 수집 시간, 추가 원본 요청 건수, 적용 기준 대조 시간, 예외 처리 시간을 기존 방식과 비교한다. 규칙 구현·회로 변경·지원 비용도 측정한다. 정확한 가격, 지불 의향, 비용 절감률은 미검증이다. 법적 책임이나 배상액 감소를 보장하는 상품으로 판매하지 않는다.

## 기말 MVP 범위

- 가상 개방형 공모펀드 세 종을 쓴다. 세 상품 모두 온라인 Ce 클래스에서 105만원 가입을 시연할 수 있다.
- 운용사 한 곳, 판매 증권사 한 곳, 가상 고객 한 명, 판매사 준법 담당자, 외부 검증자 역할을 시연한다.
- 운용사·판매사·준법 담당자·모의 거래 연동 주체는 별도 테스트 키를 쓴다. 고객 확인도 모의 키로 시연한다.
- 원장 v4에서 상품별 설명서 v1과 진단 규칙 v3을 쓴다. 각 상품 ID에 설명서 지문과 기준 투자성향을 고정한다.
- 한 임시 가입 건에 진단을 1~10회 기록할 수 있다. 고객이 가입을 중단하고 다시 시작하면 새 판매 ID를 발급한다.
- 실제 ZKP 생성·검증과 원장 거래를 시연한다. 개발과 반복 검사는 Anvil에서 한다. 외부 시연 원장은 Sepolia다. Sepolia 배포는 테스트 ETH 충전을 기다린다. [결정 기록](adr/0003-sepolia-ledger.md) 본인인증·전자서명·자금·펀드 매입 결과는 모의 처리로 표시한다.
- 모의 매입은 가입이 확정된 뒤 별도 시연으로 실행한다. 환매·만기·자금 결제·수익증권 토큰 발행·DEX는 이번 범위에서 제외한다.
- 가상 원본의 고객 다운로드와 독립 검증을 포함한다. 공인전자문서센터·상용 보관소 연동은 제외한다.
- 웹은 기관용 client 앱과 검증용 auditor 앱으로 나눈다. client 앱은 판매 채널 시연 화면도 포함한다. [결정 기록](adr/0001-web-apps-by-audience.md)
- 외부 시연은 Vercel의 웹·API 함수와 Upstash Redis로 배포한다. 상시 서버는 두지 않는다. 로컬 시연은 Docker 한 명령으로 실행할 수 있다. [배포 문서](deploy.md)

펀드 가입은 판매회사를 통해 진행할 수 있다. 매입 좌수는 적용 기준가격과 금액으로 계산한다. 구체적인 적용일과 수수료는 펀드별 문서를 따라야 한다. 아래 수치는 시연용 가정이다. [삼성자산운용 투자 프로세스](https://www.samsungfund.com/fund/insight/guide/view08.do)

| 글로벌 혁신기업 펀드 | 2등급 | 적극형 |

고객의 투자성향이 선택한 상품의 기준보다 낮으면 추가 위험 확인을 거쳐 가입할 수 있다. 실제 판매에서는 상품별 요건과 판매사 기준을 적용한다.

고객은 투자성향 결과와 상품 위험등급을 확인한다. 모든 고객이 상품 설명과 원금 손실 위험을 확인한다. 추가 안내를 받는 고객은 상품이 본인의 성향보다 위험하고, 투자권유 없이 직접 골랐으며, 가입을 계속 원한다는 점을 별도로 확인한다. 고객이 확인하고 가입하기를 선택하면 서버가 보관한 테스트 고객 키로 가입 거래를 제출한다.

두 번째 진단부터 재진단으로 표시한다. 세 번째 진단부터 준법 담당자가 해당 가입 건의 진단 이력을 검토하고 승인 데이터에 서명한다. 서명은 원장에 거래를 제출하기 전에 만든다. 답변을 다시 정정하면 같은 임시 기록에 새 회차를 추가한다. 고객 확인과 필요한 준법 승인을 새 회차에 맞춰 받는다.

### 상태와 데이터

가입 진행 중에는 임시 기록만 보관한다. 고객이 중단하면 임시 기록을 폐기한다. 원장은 최종 거래가 성공한 가입 건만 저장한다. 매입 상태는 `미요청 / 요청 접수 / 결과 대기 / 매입 결과 반영(모의)`으로 별도 표시한다. 화면은 가입 거래의 성공 영수증을 확인한 뒤 가입 완료를 표시한다.

각 판매 ID는 고객이 고른 상품·클래스·판매사·가상 고객 세션에 연결한다. 증명은 답변 커밋먼트, 규칙과 선택한 상품의 설명서 지문, 네트워크, 원장 주소, 판매 ID와 진단 회차에 연결한다. 고객 화면은 확인 전에 현재 답변의 커밋먼트를 다시 계산하고 읽기 전용 RPC로 준비된 증명을 검사한다.

컨트랙트는 최종 거래의 송신자가 등록된 테스트 고객 계정인지 확인한다. 전체 회차의 커밋먼트와 Groth16 증명, 설명 확인, 필요한 추가 위험 확인과 준법 서명을 검사한다. 거래가 성공하면 회차별 투자성향과 `EnrollmentAuthorized`, `ConditionsVerified` 등을 같은 거래에 남긴다. 필요한 경우 `HigherRiskConfirmed`도 함께 남긴다. 독립 검증은 거래 입력과 송신자, 이벤트, 성공 영수증을 대조한다.

Sepolia에는 가상 기관·상품 식별자, 무작위 판매 ID, 커밋먼트, 진단 회차, 투자성향, 확인 기록, 증명, 거래 이력이 공개될 수 있다. 답변·총점·비공개 임의값·실제 개인정보는 올리지 않는다. 증명 생성 서버는 가상 답변을 볼 수 있다. 실제 서비스의 정보 공개 범위와 네트워크는 별도로 결정한다.

가입이 확정되면 고객이 두 파일을 내려받을 수 있다. 검증 영수증은 판매·상품·버전 식별자, 네트워크·원장 주소와 가입 거래 참조를 담는다. 원본 묶음은 회차별 가상 답변·임의값과 선택한 상품의 설명서를 담는다. 검증 화면은 미리 설정한 네트워크와 원장 주소를 사용한다. 같은 환경에 남아 있는 v1·v2·v3 거래는 해당 배포 설정으로 보관 파일을 검증한다.

가입 이력에서 검증을 요청하면 판매사 API에서 해당 판매 건의 영수증과 원본만 가져온다. 브라우저가 지정한 RPC와 컨트랙트를 사용해 두 자료를 원장 기록과 대조한다. 파일 검증 경로는 판매 ID나 보관한 파일을 받으며 판매사 API를 호출하지 않는다.

| client · 온체인 처리 | 증명 생성·API·거래 제출·영수증·이벤트·상태 대조를 출처별로 보여준다. 거래 해시와 JSON을 확인한다. |
| client · 판매 채널 시연 · 펀드 찾기 | 증권사 앱에서 고객이 보는 화면이다. 상품 카드에 운용사·판매사·위험등급·보수·투자 전략을 표시한다. 세 상품 모두 상세 화면에서 클래스와 설명서를 확인하고 가입을 시작할 수 있다. |
| client · 판매 채널 시연 · 가입하기 | 가입 금액, 한 문항씩 진단, 투자성향, 핵심 설명과 필요한 추가 위험 확인을 보여준다. 최종 확인에서 가입 거래를 제출한다. 중단하면 임시 기록을 폐기한다. |
| client · 판매 채널 시연 · 내 가입 기록 | 완료한 가입 건을 보여준다. 회차별 투자성향, 가입 거래와 모의 매입 상태를 확인하고 증빙을 내려받을 수 있다. |
| auditor · 독립 검증 | 감독기관·외부 검증자가 쓴다. 가입 이력에서 검증할 건을 선택한다. 파일 검증 경로에서는 판매 ID를 입력하거나 고객 파일을 선택한다. 버전, 원본 무결성, 증명, 필수 기록을 항목별로 표시한다. |

기본 스타일은 DESIGN.md의 밝은 배경, 짙은 본문, 파란 동작 버튼, shadcn/ui 패턴을 유지한다. 상품 탐색은 넓은 카드·목록을 쓴다. 진단은 한 열에 표시한다. 기관 업무 화면은 목록과 선택한 건의 상세를 함께 본다.

## 기말 시연 시나리오

목표 시연 시간은 약 6~8분이다. 테스트넷 대기 시간은 별도다. 시간은 실제 리허설로 확인한다.

| 순서 | 발표자의 동작 | 확인할 결과 |
| --- | --- | --- |
| 1. 상품과 기준 | 운용사 화면에서 가상 펀드 세 종과 각 설명서를 등록한다. 판매사 규칙 v3도 연결한다. | 세 상품의 운용사·판매사·위험등급을 확인한다. |
| 2. 가입 중단 | 가입을 시작해 한 회차를 진단하고 중단한다. | 임시 기록이 폐기된다. 가입 거래와 완료 이력은 생기지 않는다. |
| 3. 진단과 준법 검토 | 균형성장 글로벌 펀드의 새 가입 건에서 합계 1점, 3점, 2점 순서로 진단한다. 준법 담당자가 세 회차를 검토한다. | 안정형·적극형·균형형을 확인한다. 최종 회차에는 추가 위험 확인이 필요하다. 진단과 검토는 원장 거래를 제출하지 않는다. |
| 4. 가입 확정 | 고객이 상품 설명과 추가 위험 안내를 각각 확인한 뒤 가입한다. | 한 거래가 세 회차의 증명과 필수 확인을 검증하고 가입을 기록한다. |
| 5. 모의 매입 결과 | 모의 거래 연동이 105만원, 기준가격 1,050원(1,000좌당), 매입 시 공제 비용 0원을 전달한다. | 매입 결과를 100만좌로 표시한다. 가격·좌수·자금은 모의 처리라고 표시한다. |
| 6. 사후 변경 시도 | 가상 원본 사본을 바꾼다. 완료한 판매 ID에 다시 제출하거나 다른 판매 ID에 증명을 재사용한다. | 원본 대조는 불일치를 표시한다. 컨트랙트는 중복 가입과 다른 가입 건의 증명을 거절한다. |
| 7. 독립 검증 | 가입 이력에서 검증할 건을 고른다. 파일 검증 경로에서 고객이 보관한 원본도 연다. | 두 경로에서 RPC로 같은 판매 ID와 버전·증명·이력을 확인한다. 수정한 사본은 불일치한다. |

매입 좌수 계산은 `1,050,000원 ÷ 1,050원 × 1,000좌 = 1,000,000좌`다. 기준가격 적용 시점은 모의 거래 결과의 필드로 표시한다. 블록체인 시각을 실제 펀드 기준가격 적용일로 대신하지 않는다.

사후 변경 시나리오는 탐지와 덮어쓰기 거절을 보여준다. 판매사의 원본 삭제를 원장만으로 복구한다고 설명하지 않는다. 고객의 원본도 없으면 해시만으로 내용을 복구할 수 없다. 별도 기관의 원본 보관과 장기 접근 보장은 후속 구현이다.

## 구현 순서와 현재 상태

1. 회로에서 세 가지 투자성향을 증명한다. 허용 범위를 벗어난 입력과 커밋먼트 불일치를 검사한다.
2. Foundry에서 버전 등록, 회차 고정, 단계 통제, 추가 검토, 완료 기록, 모의 매입 결과를 검증한다.
3. 고객 파일 내보내기와 판매사 API를 쓰지 않는 RPC 검증을 연결한다.
4. 기존 화면 스타일로 상품 탐색·가입·기관 업무·처리 로그를 구현한다.
5. Vercel 웹·API 함수, Upstash Redis, Sepolia로 외부 접속을 확인한다. Anvil로도 같은 코드를 리허설한다.

2026-11-08에 React 웹·Fastify API·Circom 회로·Solidity 원장을 처음 구현했다. v2에서 투자성향 분류와 직접 청약의 추가 위험 확인을 추가했다. v3에서 가입을 한 거래로 묶었다. v4는 기존 Groth16 회로와 증명 키를 사용한다. 상품 세 종의 가입을 지원하며 진단 규칙 v3으로 선택한 상품의 설명서와 기준 투자성향을 확인한다. v1·v2·v3·v4의 판매 건은 각 배포의 원장 주소로 구분한다. [실행 안내](runbook.md)에 재현 명령과 검사 범위를 기록했다. 현재 시연 원장은 Anvil이다. 2026-11-12에 API를 Vercel 함수와 공유 저장소로 실행할 수 있게 바꿨다. 웹을 client·auditor 앱으로 나눴다. Sepolia 배포와 Vercel 첫 배포는 남아 있다. 개발 스택은 README를 따른다.
