# MVP 실행과 시연

2026-11-13. 원장 v5. 현재 시연 환경은 로컬 Anvil이다. 외부 시연은 Vercel과 Sepolia로 배포한다. Sepolia 배포는 테스트 ETH 충전을 기다린다. [배포 문서](deploy.md)

웹은 페이지 세 개다. 진입 화면(`/`), 판매사 콘솔과 판매 채널 시연(`/client/`), 감독기관 화면(`/auditor/`)이다. [결정 기록](adr/0006-seller-console-and-single-web-app.md)

## 실행

Docker로 실행하면 Node 설치가 필요 없다.

```bash
docker compose up --build
```

Node로 실행하려면 프로젝트 루트에서 Node 22.x를 사용한다.

```bash
npm ci
npm run dev
```

[진입 화면](http://127.0.0.1:5173/), [client](http://127.0.0.1:5173/client/), [auditor](http://127.0.0.1:5173/auditor/), [API 상태](http://127.0.0.1:3001/api/health)를 확인한다. API 상태는 RPC 연결과 체인 ID, 원장 코드, 판매 기록 저장소를 점검한다. 모두 정상이면 200, 하나라도 실패하면 503과 실패한 항목을 돌려준다. `npm run dev`는 기존 Anvil을 재사용한다. 원장 버전과 증명 키가 같으면 배포도 재사용한다. 원장 버전이나 증명 키를 변경하면 배포를 갱신한다. 로컬 계정은 Anvil의 공개 테스트 mnemonic에서 만든다. 역할마다 다른 주소를 쓴다.

**개발할 때.** 개발도 Docker로 한다. `compose.yaml`이 `apps/`, `packages/`, `scripts/`를 컨테이너에 마운트한다. 그래서 코드를 고치면 다시 빌드하지 않아도 반영된다. Node(`npm run dev`)로 실행해도 같다.

| 고친 곳 | 반영 방법 |
| --- | --- |
| 웹(`apps/web`, `packages/ui`) | 저장하면 브라우저에 바로 반영된다(Vite HMR). |
| API, 코어(`apps/api`, `packages/core`) | 저장하면 API가 다시 시작한다(`tsx watch`). 진행 중인 요청은 끊긴다. |
| 원장·회로(`contracts`, `circuits`) | 다시 빌드한다(`docker compose up --build -d`). 원장 버전이나 증명 키가 바뀌면 새로 배포한다. |
| 의존성(`package.json`), `Dockerfile` | 다시 빌드한다(`docker compose up --build -d`). |

로그는 `docker compose logs -f`로 본다. Docker와 Node 실행은 같은 포트(5173, 3001, 8545)를 쓰므로 한 번에 하나만 띄운다.

**v4에서 올릴 때.** v5 코드로 처음 실행하면 증명 키를 새로 만들고(약 3분) 원장 v5를 새 주소에 배포한다. 이전 v4 배포 설정은 `.local/deployment-local-v4.json`으로 남는다. v4 판매 기록은 v4 원장 주소에 그대로 있지만 v5 화면은 v5 원장만 읽는다. Docker에서 `circuits/build/`를 호스트에 마운트해 v4 시연을 계속 쓰려면, 올리기 전에 그 폴더를 백업한다.

## 발표 순서

시연 답변은 [PRD 시연 진단 기준 v1](prd.md#시연-진단-기준-v1)의 선택지 순서로 적는다. 순서는 연령, 투자 목적, 투자 비중, 투자 경험, ELS 이해도, 감내할 수 있는 손실이다.

1. **기준 등록.** 진입 화면에서 **판매사 콘솔**을 연다. **상품 관리**에서 **상품·진단 기준 등록**을 누른다. **진단 기준**에서 문항, 점수, 추출 제한, 등급 구간, 등급별 판매 상품을 보여 준다. 감독기관 화면의 **기준 감사**에서 같은 기준 해시와 원문 대조 결과를 보여 준다.
2. **진단과 중단.** **판매 채널 시연 › 상품 찾기**에서 `고난도 금융투자상품` 표시가 붙은 가상 글로벌지수 스텝다운 ELS를 연다. 가입을 시작하고 `49세 이하 / 예금 이자 이상의 수익 / 10~30% / 펀드 / 모름 / 원금 20%까지`로 답한다. 1회차는 위험중립형이다. **가입 중단하기**를 누른다. 진단 1회차는 원장에 남는다.
3. **다시 시작.** 같은 상품에서 가입을 다시 시작한다. 화면이 이전 결과를 보여 주면 **다시 진단하기**를 누른다. 2회차는 ELS 이해도만 `들어 본 적 있음`으로 바꾼다(7점, 적극투자형). 3회차는 `49세 이하 / 높은 수익 / 10% 이하 / ELS·파생상품 / 들어 본 적 있음 / 원금 20%까지`로 답한다(10점, 공격투자형). "원금 20%까지"의 추출 제한 때문에 권유 가능 위험등급은 2등급까지다. 3회차부터 관리자 승인이 필요하다는 안내가 나온다.
4. **관리자 승인.** **판매·검토**에서 해당 판매 건의 회차 이력을 보고 **관리자 승인**을 누른다. **위험 신호**에서 재진단 반복과 결과 상승 신호를 확인한다.
5. **부적합 청약.** 가입 화면으로 돌아간다. 1등급 ELS는 이 고객에게 권유하지 않는다는 안내와 판매대상 고객군이 나온다. 추가 위험 확인에 체크하고 핵심 설명 카드 5장을 읽는다. 녹취에 동의하고 청약한다. 청약 거래가 성공하고 숙려기간 60초가 시작된다.
6. **숙려와 확정.** **시연: 숙려 중에 최종 확인 시도하기**를 누른다. 원장이 거절한다. 60초가 지나면 **최종 확인**을 누른다. 가입이 확정되고 증명서가 나온다.
7. **사후 변경 시도.** **판매·검토**에서 **사후 변경 시도**로 2회차를 다시 기록하려 한다. 원장이 `InvalidAttempt`로 거절한다. **온체인 처리**에서 진단 기록, 청약, 최종 확인 거래와 이벤트를 출처별로 보여 준다.
8. **고객 검증.** **내 가입 기록**에서 증명서와 원본을 내려받고, **변경한 원본 내려받기**로 답변 하나를 바꾼 사본도 받는다. **가입 기록 확인**에서 증명서 번호로 확인하면 `일치`다. 바꾼 원본으로 확인하면 `불일치`(원본 답변 대조)다.
9. **감독기관 조회.** 감독기관 화면의 **분쟁 조회**에서 같은 판매 ID를 연다. 원장만 대조한 결과와 판매사 제출 자료를 넣은 결과를 함께 보여 준다. **대시보드**, **위험 신호**, **보고서**(JSON·CSV)도 판매사 API 없이 원장에서 만든다.

적합한 상품은 가상 원금지급형 ELB로 보여 줄 수 있다. 3회차 결과로 ELB를 청약하면 적합이고 녹취·숙려 대상이 아니다. 관리자 승인은 판매 건마다 받으므로 이 청약도 승인이 필요하다.

시연 데이터를 미리 채우려면 `npm run demo -- --api <API 주소> --rpc <RPC 주소>`를 실행한다. 진단 3회, 관리자 승인, 확정한 ELS·ELB 가입을 만든다. 결과는 `.local/demo/v5/`에 둔다. Anvil에서는 숙려기간을 시간 이동으로 건너뛴다. 그래서 이 데이터를 채운 뒤에는 화면의 숙려 남은 시간이 실제보다 길게 보일 수 있다.

## 검증 절차

| 검사 | 확인할 내용 |
| --- | --- |
| Foundry 단계·권한 검사 (17개) | Verifier stub으로 역할 권한, 회차 순서와 재기록 거절, 기준·상품 버전, 적합성, 추가 위험 확인, 관리자 승인 서명, 녹취 지문, 숙려 전 확정 거절, 철회, 모의 결제를 확인한다. |
| 실제 회로·API 통합 검사 | 별도 Anvil에 실제 Verifier를 배포한다. 중단 뒤에도 회차가 이어지는지, 관리자 승인, 부적합·녹취 청약, 숙려, 검증 결과 세 가지, 사후 변경 거절, 증명 재사용 거절, 등록하지 않은 기준 거절, 범위 밖 답변, 위험 신호를 검사한다. |
| 코어 검사 | 진단 기준 검사, 기준 해시, 판정 계산을 검사한다. |
| 감독기관 대조 | 모든 화면이 지정 RPC의 원장에서 읽는다. 분쟁 조회에서 판매사 제출 자료를 받을 때만 판매사 API에 GET을 보낸다. |

`npm run contracts:test`, `npm test`, `npm run build`로 재현한다. 통합 테스트는 별도 포트와 임시 디렉터리를 사용한다. 기본 시연 원장의 데이터를 바꾸지 않는다. 증명 키를 다른 폴더에 두고 검사하려면 `FINVERIC_ZK_DIR`을 지정한다.

## Sepolia와 외부 배포

배포 순서, 환경 변수, 한도는 [배포 문서](deploy.md)를 따른다.

API는 배포 때 쓴 것과 **같은** 증명 키(zkey)와 WASM을 사용해야 한다. 증명 키를 교체하면 기존 Verifier와 맞지 않는다. 키 지문이 배포 설정과 다르면 API 시작과 Vercel 빌드를 거절한다. Sepolia 배포 뒤 `npm run release:sepolia`로 `deploy/sepolia/`에 배포본을 만들고 커밋한다.

## 오류와 복구

- **상품·기준 등록 전 가입 거절.** 상품 관리에서 **상품·진단 기준 등록**을 누른다.
- **청약 거절.** 원장이 거절 이유를 돌려준다. 부적합이면 추가 위험 확인, 3회차 이상이면 관리자 승인, 녹취 대상이면 녹취 동의가 필요하다. 청약은 고객의 최신 회차만 쓸 수 있다.
- **숙려 전 확정 거절(`TooEarly`).** 숙려 남은 시간이 끝난 뒤 다시 누른다.
- **영수증 대기:** 해시를 확인하고 기다린다. 거래를 다시 보내지 않는다. 온체인 처리에서 새로 조회한다.
- **RPC 연결 실패:** 네트워크 ID와 RPC 설정을 확인한다. 실패를 완료로 표시하지 않는다.
- **증명 키 불일치:** 기존 키를 복원하거나 새 Verifier와 원장을 배포한다. 기존 고객 파일의 원장 주소는 바뀌지 않는다.
- **로컬 초기화:** 서버를 종료한 뒤 `.local/`을 백업한다. 보관할 이력이 없을 때만 다른 디렉터리로 이동한다. 다음 실행은 새 원장을 배포한다.

원본을 잃으면 원장 해시로 내용을 복구할 수 없다. 별도 기관의 장기 보관은 후속 범위다. 증명 키는 단일 운영자의 시연용 trusted setup이다. 실제 운영용 MPC ceremony와 보안 감사는 수행하지 않았다.
