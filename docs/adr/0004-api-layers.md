# 0004. API는 계층형 구조로 나누고 DDD는 쓰지 않는다

2026-11-12 · 결정됨

## 맥락

API 업무 로직은 `service.ts` 한 파일(766줄)에 있었다. 이후 업무 모듈로 나눴지만 경계가 남아 있었다. 경로가 `app.ts` 한 곳에 있었다. 모듈이 판매 기록 배열과 RPC 클라이언트를 직접 썼다. 참고한 cocoa 저장소는 NestJS의 컨트롤러 → 서비스 → 리포지토리 계층형 구조다. DDD의 애그리거트·값 객체는 쓰지 않는다.

## 결정

| 계층 | 위치 | 역할 |
| --- | --- | --- |
| 경로 | `apps/api/src/routes/` | 요청 검사, `FundService` 호출 |
| 실행 맥락 | `apps/api/src/service.ts` | 배포 설정, 역할 키, RPC, 리포지토리, 시작 검사 |
| 업무 절차 | `apps/api/src/modules/` | 담당자별 절차 |
| 리포지토리 | `apps/api/src/repositories/` | 판매 기록 조회·변경·저장, 잠금 |
| 게이트웨이 | `apps/api/src/gateways/` | 원장(EVM)과 증명(snarkjs) 연동 |

- 요청은 위에서 아래로만 흐른다. 아래 계층은 위 계층을 import하지 않는다.
- API 계약(DTO)은 `packages/core/src/api.ts` 한 곳에 둔다. API와 웹이 함께 쓴다.
- 프레임워크는 Fastify를 유지한다. NestJS와 의존성 주입 컨테이너는 쓰지 않는다.

## 이유

- 업무 규칙의 최종 판정은 스마트컨트랙트가 한다. 서버에 애그리거트를 만들면 같은 규칙을 한 번 더 구현하게 된다. 그래서 DDD 대신 계층형을 쓴다.
- 리포지토리를 두면 저장 방식(파일, Redis, 나중의 PostgreSQL)을 바꿔도 업무 모듈을 고치지 않는다.
- 게이트웨이를 두면 원장 호출이 한 파일에 모인다. 모듈은 무엇을 기록할지만 다룬다.
- API는 약 1,600줄이다. 프레임워크를 바꿀 만큼 크지 않다.

## 대가

- 파일 수가 늘었다(경로 4개, 리포지토리 2개, 게이트웨이 2개).
- 판매 건 필드는 모듈이 직접 바꾼 뒤 `repository.save()`를 부른다. 상태 변경 규칙이 한 객체에 모여 있지 않다. 업무가 커지면 판매 건을 애그리거트로 묶는 방식을 다시 검토한다.

## 검토한 대안

- **DDD(애그리거트·값 객체·도메인 이벤트).** 규칙 판정을 원장이 하므로 중복이 크다.
- **NestJS로 전환.** 계층은 같고 프레임워크와 데코레이터만 늘어난다.
