# 0006. client는 판매사 콘솔로, auditor에 고객 검증 페이지를 둔다

2026-11-12 · 제안 · [0001](0001-web-apps-by-audience.md)의 사용자 범위와 루트 경로를 바꾼다

## 맥락

[0001](0001-web-apps-by-audience.md)은 웹을 두 앱으로 나눴다. client는 운용사·증권사·준법 담당자, auditor는 감독기관·외부 검증자가 쓴다. 투자자는 FINVERIC 화면을 직접 쓰지 않는다. 루트 `/`는 `/client/`로 보낸다.

금소법의 6대 판매원칙(적합성 원칙, 설명의무 등)은 금융상품판매업자가 지킨다. 불완전판매로 제재받는 쪽도 판매사다. H지수 ELS 제재(2026-11-04) 대상은 은행 7곳과 증권사 6곳이었다. 모두 판매사 자격이었다. 상품을 만든 제조사(운용사, 발행사)는 투자설명서 내용의 정확성에 책임을 진다. 판매 절차에 대한 책임은 지지 않는다.

FINVERIC이 남기는 기록은 판매사가 판매원칙을 지켰다는 증거다. 판매사는 판매 절차 시스템을 직접 만들고 운영하는 대신 FINVERIC을 쓰고, 상품과 판매에 집중한다.

사용자는 client가 할 일로 진단 기준(질문지, 형식, 등급) 관리와 등급별 상품 관리를 요청했다. auditor에는 원장으로 검증하고 결과를 확인하는 기능을 요청했다.

팀 조사(2026-11-12)는 두 가지를 더한다.

- 서비스의 핵심 주장은 "고객이 판매사를 거치지 않고 기록을 확인한다"이다. 고객은 협회가 운영하는 검증 페이지에서 직접 검증한다.
- ELS 위험등급은 판매사가 발행사 신용위험을 반영해 정한다.

## 결정

- **client는 판매사 콘솔이다.** 판매사는 금융상품판매업자다. 증권사, 은행, 펀드를 직접 파는 자산운용사가 해당한다. 판매사는 진단 기준과 판매하는 상품을 등록한다. 진단 계산, 적합성 판정, 원장 기록, 증명, 검증 화면은 FINVERIC이 맡는다.
- **client 사용자는 판매사의 소비자보호 담당이다.** 진단 기준, 상품, 설명서 버전, 위험등급, 판매대상 고객군을 등록한다. 3회차 이상 진단한 고객의 청약에 관리자 승인을 한다. 위험 신호를 처리한다. 관리자 승인은 별도 키로 한다.
- **제조사는 client가 아니다.** 상품 정보에 운용사·발행사 이름만 표시한다. 제조사가 상품을 직접 등록하는 참여 방식은 MVP 이후 후보로 둔다.
- **client 메뉴:** 대시보드, 진단 기준 관리, 상품 관리, 판매·검토, 위험 신호, 온체인 처리, 판매 채널 시연.
- **auditor는 감독기관 화면과 고객 검증 페이지를 함께 둔다.**
  - 감독기관 메뉴: 대시보드, 분쟁 조회, 기준 감사, 상품 감사, 위험 신호, 보고서.
  - 고객 검증 페이지: `/auditor/verify`. 로그인 없이 연다. 운영 주체를 협회로 표시한다. 증명서 번호, QR, 파일로 검증한다. 블록체인 용어를 숨기고 해요체를 쓴다. 결과는 `일치`, `불일치`, `기록 없음`이다.
- **고객이 쓰는 FINVERIC 화면은 고객 검증 페이지 하나다.** 고객의 가입 화면은 판매사 앱이다. 시연에서는 client의 판매 채널 시연이 증권사 앱을 재현한다.
- **루트 `/`는 진입 화면이다.** 역할 카드 3개(판매사 콘솔, 감독기관, 고객 검증), 시연 순서, 연결된 원장과 상태를 보여 준다. 빌드 도구 없는 정적 HTML 한 장으로 만든다. 두 앱과 같은 색 토큰을 쓴다. 상태는 `/api/health`로 읽는다. Vercel은 `/`에서, 로컬은 client 개발 서버의 `/`에서 제공한다.
- **두 앱 구조와 경로는 유지한다.** `/client/`, `/auditor/`, `/api`는 그대로다.
- **용어.** client 사용자는 "소비자보호 담당"이다. 3회차 이상 진단한 고객의 청약 승인은 "관리자 승인"이다. 팀 조사와 금감원 권고의 용어를 따른다. "준법"은 쓰지 않는다. 코드 식별자는 v5 구현 때 맞춘다.
- **서비스 이름은 팀이 정할 때까지 FINVERIC을 쓴다.** 팀 조사의 가칭은 "세일즈 블랙박스"다.

## 이유

- 판매원칙을 지킬 책임이 있는 쪽이 판매사다. 이 서비스가 필요하고 비용을 낼 이유가 있는 쪽도 판매사다.
- 판매사가 위험등급을 정하므로 상품 등록도 판매사가 한다. 위험등급을 정하는 쪽과 등록하는 쪽이 같다.
- client 역할이 하나라서 메뉴와 권한 키가 단순하다.
- 고객이 직접 검증하는 화면이 없으면 "판매사를 거치지 않는 검증"을 시연할 수 없다.
- 고객 검증 페이지와 감독기관 화면은 같은 검증 로직을 쓴다. 둘 다 지정 RPC로 원장을 읽고 판매사 API를 쓰지 않는다. 그래서 앱을 하나 더 만들지 않고 auditor에 둔다.
- 진입 화면은 업무 로직이 없다. React 앱을 하나 더 만들 필요가 없다.

## 대가

- v4의 운용사 화면(상품·문서 관리)이 사라진다. 운용사가 여러 판매사에 같은 상품 버전을 한 번에 전달하는 기능도 MVP에서 빠진다.
- 판매사가 상품 정보를 직접 입력한다. 제조사의 설명서와 판매사가 등록한 설명서가 같은지는 원장이 보장하지 않는다.
- auditor 앱의 사용자가 두 집단이다. 문구 규칙이 둘이다. 감독기관 화면은 기술 정보를 보여 주고, 고객 페이지는 숨긴다.
- 정적 진입 화면은 공통 React 컴포넌트를 쓰지 못한다. 색 토큰은 CSS 변수로 맞춘다.
- FINVERIC이 판매 절차 시스템을 제공해도 법적 책임은 옮겨 오지 않는다. 영업 자료에서 책임 이전처럼 설명하지 않는다.
- "투자자는 FINVERIC 화면을 쓰지 않는다"는 규칙에 예외가 생긴다. AGENTS.md, DESIGN.md, README를 함께 고친다.
- 화면 캡처와 그림을 다시 만든다.

## 검토한 대안

- **제조사도 client 역할로.** 운용사와 발행사가 상품을 한 번 등록하면 여러 판매사가 같은 버전을 쓴다. 제조사는 판매 절차에 대한 책임이 없어 이 서비스를 쓸 이유가 약하다. 역할과 키가 늘어난다.
- **고객 검증 페이지를 별도 앱으로.** 고객과 감독기관의 배포·문구를 완전히 나눈다. 같은 검증 로직을 두 앱이 쓰고 개발 서버가 세 개가 된다.
- **고객 검증을 client 앱에.** 판매사가 만든 화면의 검증은 독립 검증이 아니다.
- **협회 콘솔을 따로.** 협회의 표준 기준 등록은 MVP 범위 밖이다. 화면에 운영 주체로만 표시한다.
- **진입 화면을 client 앱의 첫 화면으로.** 판매사 콘솔과 역할 선택이 섞인다. 고객과 감독기관이 판매사 앱을 거쳐 들어오게 된다.
