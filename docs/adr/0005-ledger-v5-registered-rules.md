# 0005. 원장 v5: 진단 기준을 등록하고 진단 회차마다 기록한다

2026-11-12 · 제안 · [PRD v5](../prd.md#판매-절차와-원장-기록)

## 맥락

v4 원장과 회로는 진단 기준을 코드에 고정한다.

- 회로 `suitability.circom`은 문항 2개, 선택지 0~2점, 투자성향 3단계를 계산한다.
- 원장 `registerRule`은 규칙 v3 하나만 받는다. `registerProduct`는 상품마다 한 번만 등록한다. 상품에는 기준 투자성향 하나만 있다.
- 진단 회차는 서버에 임시로 둔다. 가입 거래 한 건(`completeEnrollment`)이 모든 회차를 함께 기록한다. 고객이 가입을 중단하면 임시 기록을 지운다.

팀 조사(2026-11-12)로 두 가지가 정해졌다.

- 기준은 투자성향 5단계, 상품 위험등급 6단계다. 점수 방식과 추출 방식을 함께 쓴다. 시연의 중심은 고난도 금융투자상품(ELS)이다. 펀드 같은 다른 상품 유형도 함께 다룬다. 숙려기간과 최종 의사 확인 단계가 있다.
- 핵심 주장은 "판매사도 기록을 바꾸거나 숨길 수 없다"이다. 반복 성향 분석(하나은행 양매도 ETN, 2019)이 대표 사례다.

v4에서는 판매사가 가입을 중단시키고 새 판매 ID로 다시 시작할 수 있다. 그러면 이전 회차가 원장에 남지 않는다. 핵심 주장과 맞지 않는다. 판매사가 문항, 점수, 등급을 관리하려면 기준이 코드가 아니라 데이터여야 한다.

## 결정

### 진단 기준을 데이터로 등록한다

- 진단 기준 원문은 JSON 한 개다. 문항, 선택지 점수, 추출 조건, 고령 표시, 등급 구간, 적합성 기준(투자성향별 권유 가능 최고 위험등급)을 담는다.
- 원문을 정해진 순서의 필드 배열로 바꾼다. 문항 문구를 포함한 원문 전체의 지문도 배열에 넣는다. 배열의 Poseidon 해시가 **기준 해시**다.
- 원장은 기준 해시를 여러 버전 등록할 수 있다. 같은 해시는 다시 등록하지 못한다. 수정·삭제 함수는 두지 않는다.
- 기준 원문은 공개 자료다. 감독기관은 원문으로 해시를 다시 계산해 원장과 대조한다.

### 회로 v5는 고정 크기의 범용 회로다

- 최대 크기: 문항 10개, 문항당 선택지 5개, 투자성향 5단계, 위험등급 6단계. 덜 쓰는 문항은 선택지 하나(0점)로 채운다.
- 기준 값은 비공개 입력이다. 회로가 기준 해시를 계산하고 공개 입력과 같은지 검사한다. 그래서 등록하지 않은 기준이나 바꾼 값으로는 유효한 증명을 만들 수 없다.
- 회로는 다음을 계산한다.
  - 답변이 선택지 범위 안에 있는지 검사한다.
  - 답변 커밋먼트 = Poseidon(답변 10개, 임의값).
  - 점수 합계와 등급 구간으로 투자성향(1~5)을 계산한다.
  - 권유 가능 최고 위험등급 = 적합성 기준값과 고른 선택지의 추출 조건 중 가장 보수적인 값.
  - 고령 표시 = 고른 선택지의 표시 값.
- 공개 신호: 커밋먼트, 체인 ID, 원장 주소, 고객 가명 ID, 회차, 기준 해시, 투자성향, 권유 가능 최고 위험등급, 고령 표시.
- 진단 증명은 판매 건이나 설명서에 묶지 않는다. 고객이 상품을 고르기 전에 진단하기 때문이다. 상품과의 연결은 청약 거래가 한다.

### 진단 회차마다 원장에 기록한다

- 진단 회차마다 거래 한 건을 보낸다. 송신자는 판매사 키다.
- 회차는 고객 가명 ID로 센다. 원장이 다음 회차 번호를 정하고, 증명의 회차와 같은지 검사한다. 판매사는 회차를 건너뛰거나 다시 쓸 수 없다.
- 고객 가명 ID는 판매사 비밀값과 고객 번호의 해시다. 판매사 사이에는 연결하지 않는다.

### 청약과 최종 확인을 나눈다

- **청약 거래**(고객 키): 판매 ID, 상품 버전, 사용한 회차, 설명 확인과 확인 시간, 필요한 추가 위험 확인·관리자 승인·녹취 지문을 기록한다. 원장은 아래를 검사한다.
  - 사용한 회차가 그 고객의 최신 회차인가.
  - 상품 위험등급이 권유 가능 최고 위험등급 안인가. 아니면 추가 위험 확인이 있는가.
  - 회차가 3 이상이면 관리자 승인이 있는가.
  - 녹취 대상이면 녹취 지문이 있는가. 녹취 대상은 고난도 상품, 또는 65세 이상·부적합 고객에게 파는 파생결합증권이다.
- **최종 확인 거래**(고객 키): 숙려 대상이면 청약 뒤 최소 경과 시간이 지나야 한다. 성공하면 가입을 확정한다. 철회 거래도 둔다.
- 최소 경과 시간은 배포 때 정한다. 영업일 계산은 판매사 시스템이 한다. 시연 값은 Anvil 2영업일(시간 이동), Sepolia 60초다.

### 상품은 버전으로 등록한다

- 상품, 진단 기준, 진단 기록의 송신자는 모두 판매사 키다.
- 상품 버전은 상품 유형, 설명서 지문, 위험등급(1~6), 고난도 여부, 파생결합증권 여부를 가진다.
- 같은 상품의 같은 버전은 다시 등록하지 못한다. 청약은 그 상품의 최신 버전을 쓴다.

### 버전과 이전 기록

- `ledgerVersion`은 5다. v5는 새 주소에 배포한다.
- v4 이하 판매 건은 이전 주소에 그대로 남는다. v5 화면은 v5 원장만 검증한다. 이전 버전 검증 경로는 v5 구현 때 지운다. 외부 시연 원장(Sepolia)에는 이전 버전이 없다.

## 이유

- 판매사가 가입을 중단시켜도 진단 이력이 원장에 남는다. 회차 번호를 원장이 정하므로 회차를 숨기거나 바꿀 수 없다.
- 최신 회차만 청약에 쓰게 해서 유리한 이전 결과를 고르지 못하게 한다.
- 기준을 바꿀 때 회로, 증명 키, Verifier를 다시 만들지 않는다. 판매사는 화면에서 기준을 관리한다.
- 해시만으로는 판정이 기준대로인지 증명하지 못한다. ZKP를 유지해야 감독기관이 원문 없이 판정을 확인한다.
- 기준 값을 공개 입력으로 넘기면 공개 입력이 100개를 넘는다. 공개 입력마다 Verifier gas가 늘어난다. 그래서 비공개 입력과 해시 대조를 쓴다.

## 대가

- **거래 수.** 가입 한 건에 거래가 "진단 회차 수 + 2"건이다(청약, 최종 확인). v4는 가입 거래 한 건이다. 시연(진단 3회)은 5건이다.
- **대기 시간.** Sepolia에서 거래마다 약 12초를 기다린다. 시연 대기가 약 1분이다. 숙려 시연 60초가 더해진다.
- **가스.** v4 측정값으로 진단 거래는 약 30만 gas다([0003](0003-sepolia-ledger.md)). 시연 가입 한 건은 약 110만 gas로 예상한다. v4 평균은 약 76만이다. 공개 입력 수가 비슷해서 진단 거래 gas는 크게 늘지 않는다고 본다. 구현 뒤 다시 측정한다.
- **회로 크기.** 기준 해시 계산 때문에 제약 수가 수천~1만 개로 늘어난다고 예상한다. 지금 ptau는 2^11(2,048 제약)이다. 2^14로 키운다. 증명 생성 시간은 구현 뒤 측정한다. Vercel 함수 한도 300초 안이어야 한다.
- **공개 범위.** 중단한 가입의 진단 결과도 공개 원장에 남는다. 커밋먼트, 투자성향, 권유 가능 위험등급, 고령 표시, 고객 가명 ID다. 같은 고객 가명 ID의 회차가 서로 연결된다. 원문, 총점, 고객 번호는 남지 않는다. 공개 투자성향으로 총점 구간을 알 수 있다.
- **기준 크기 제한.** 문항 10개, 선택지 5개를 넘는 기준은 등록하지 못한다. 늘리려면 회로와 키를 다시 만든다.
- **새 키와 원장.** 증명 키, Verifier, 원장 주소가 바뀐다. Sepolia는 아직 배포 전이라 재배포 비용은 없다.
- **API 변경.** 진단마다 원장 거래를 기다린다. 임시 기록과 폐기 절차가 바뀐다.

## 검토한 대안

- **v4 유지(가입 거래 한 건).** 거래가 적고 중단한 가입의 흔적이 없다. 판매사가 중단과 재시작으로 회차를 숨길 수 있다.
- **판매 ID 기준 회차.** 구현이 v4와 가깝다. 새 판매 ID에서 회차가 다시 1이 된다.
- **기준마다 회로 생성.** 회로가 작고 단순하다. 기준을 바꿀 때마다 trusted setup과 Verifier 배포가 필요하다. 판매사가 화면에서 기준을 관리하지 못한다.
- **해시만 기록(ZKP 제거).** 구현이 가장 쉽다. 판매사가 판정 결과를 임의로 기록할 수 있다.
- **단계마다 거래(진단, 적합성, 설명, 청약을 각각).** 조사의 "단계별 기록"에 가장 가깝다. 적합성·설명·청약은 고객이 한 흐름에서 확인하므로 한 거래로 묶어도 순서는 지켜진다. 거래만 늘어난다.
