## 서비스 정의

**증권사와 발행사가 금융상품의 판매 조건을 확인하고, 청약의 접수·취소·배정 상태를 같은 원장에서 관리하는 B2B 플랫폼이다.**

고객은 증권사 화면에서 상품을 고르고 청약한다. 플랫폼은 증권사와 발행사 시스템을 연결한다. 각 기관은 자기 권한으로 업무를 처리한다. 준법팀과 권한을 받은 외부 검증자는 같은 청약 ID로 처리 근거를 확인한다.

발행사와 판매사는 업무 역할을 구분한 용어다. 반드시 서로 다른 회사는 아니다. ELS는 증권회사가 발행한다. 같은 증권회사가 자기 ELS를 판매하면 두 역할을 함께 맡는다. 이 경우 상품 운영과 고객 판매 업무를 구분하되, 별도 발행회사를 가정하지 않는다. [삼성증권 ELS/DLS 거래안내](https://www.samsungpop.com/ux/kor/customer/guide/workproductguide/elsDlsDeal.do)

발행사는 상품과 모집 조건을 등록한다. 판매사는 고객의 판매 조건을 확인하고 청약을 접수한다. 계좌 시스템은 청약 자금의 확보·납입·반환을 처리한다. 블록체인은 기관이 공유하는 청약 상태와 조건 검사를 담당한다. 실제 기관의 참여와 운영 권한은 아직 협의하지 않은 설계 가정이다.

아래의 복수 판매사 시연은 기관 간 처리를 보여주기 위한 가정이다. ELS의 기본 구조에 별도 발행회사와 복수 판매사가 필요하다는 뜻은 아니다. 한 증권사의 자체 발행·판매만 대상으로 삼으면, 기관 간 기록 대조 문제의 적용 여부를 다시 확인해야 한다. 그 경우 블록체인의 가치는 외부 검증자가 판매사 시스템과 별도로 근거를 확인하는 데서 검증한다.

## 해결하려는 문제

다음은 제품이 검증할 문제 가설이다. 실제 발생 빈도와 비용은 증권사·발행사 인터뷰와 파일럿에서 확인해야 한다.

| 업무 | 문제 가설 | 플랫폼이 제공할 기능 |
| --- | --- | --- |
| 상품 판매 준비 | 상품 조건과 설명서 버전이 바뀌면 기관별 적용 버전을 다시 대조해야 한다. | 상품 ID에 판매 기간·설명서·규칙 버전을 연결한다. |
| 청약 접수 | 진단·설명 확인·서명 조건이 충족됐는지 사후에 다시 확인해야 한다. | 필수 조건을 확인해야 접수 상태로 전환한다. |
| 접수와 취소 전달 | 기관별 기록이 달라 접수 건과 취소 건을 대조해야 한다. | 기관들이 같은 청약 ID와 상태를 조회한다. |
| 마감과 배정 | 취소 건 제외, 모집 한도, 배정 규칙을 맞춰야 한다. | 마감 시점의 유효 청약을 기준으로 배정한다. |
| 민원과 점검 | 여러 시스템의 기록을 모아 처리 순서를 재구성해야 한다. | 적용 규칙과 처리 이력을 같은 청약 ID로 조회한다. |

## 사용자와 구매자

| 사용자 | 맡는 업무 |
| --- | --- |
| 투자자 | 상품을 확인한다. 진단에 답하고 모의 서명한다. 청약·취소를 요청하고 결과를 확인한다. |
| 판매 증권사 | 고객과 판매 증빙을 관리한다. ZKP를 생성하고 청약 접수·취소를 요청한다. 처리 예외를 확인한다. |
| 발행사 | 상품과 모집 조건을 등록한다. 모집을 마감하고 배정을 실행한다. |
| 계좌 시스템 | 자금 확보·납입·반환 결과를 청약 ID에 연결해 전달한다. MVP는 모의 결과를 쓴다. |
| 준법팀·외부 검증자 | 권한 범위에서 처리 근거를 조회한다. 판매사 API와 별도로 원장을 확인한다. |
| 플랫폼 운영자 | 기관별 접근 권한, API 연결, 서비스 운영을 관리한다. |

첫 구매자는 증권사의 디지털채널·상품 운영 조직으로 가정한다. 준법팀과 IT·보안 조직도 도입을 검토한다. 여러 판매사의 청약을 받는 발행사도 구매자 후보다. 감독기관의 공식 참여와 증빙 채택은 확정하지 않았다.

## 핵심 기능

1. **공통 상품 등록.** 상품 ID, 판매사 권한, 청약 기간, 모집 한도, 설명서 버전, 규칙 버전, 배정 방식을 등록한다.
2. **접수 전 조건 검증.** ZKP로 진단 점수와 위험 확인 조건의 충족을 증명한다. 컨트랙트는 같은 청약 건의 모의 서명 확인, 설명서 버전, 모의 자금 확보 확인도 검사한다.
3. **공동 청약 처리.** 접수·취소·마감·배정의 순서와 역할을 검사한다. 같은 요청이 중복 접수되거나 마감 후 취소되지 않도록 한다.
4. **계좌 시스템 연결.** 청약 ID로 자금 확보·납입·반환 결과를 연결한다. 자금 확보만으로 접수 완료를 표시하지 않는다. 원장 거래 결과도 확인한다.
5. **마감과 배정.** 마감 뒤 유효한 접수 건만 모아 배정한다. 취소한 건은 제외한다. 기말 시연에서는 고정한 안분 배정 규칙을 컨트랙트에서 실행한다.
6. **역할별 업무와 검증 화면.** 투자자, 판매사, 발행사, 검증자 화면을 한 웹사이트의 사이드 탭으로 제공한다. 처리 화면은 실제 거래 해시·영수증·이벤트를 표시한다.

시연용 진단은 손실 감내와 투자 경험 두 문항을 쓴다. 각 문항은 0~2점이다. 합계 3점 이상이어야 한다. 별도 위험 확인 문항에도 통과해야 한다. 실제 증권사의 적합성 판정표를 재현하는 규칙은 아니다.

### 블록체인과 ZKP가 맡는 일

블록체인은 기관들이 같은 청약 상태와 처리 순서를 확인할 기준을 제공한다. 스마트컨트랙트는 권한, 접수 조건, 상태 전환, 배정 규칙을 검사한다. 계좌 처리 결과는 권한을 받은 계좌 연동 주체가 전달한다. 컨트랙트가 은행 잔액이나 실제 납입을 직접 확인하는 것은 아니다.

ZKP는 고객이 확인해 고정한 답변이 진단 규칙을 충족했음을 증명한다. 고객 답변과 점수는 공개하지 않는다. 회로는 선택지 범위, 배점, 합계 기준, 위험 확인을 검사한다. 공개 입력은 원장 도메인, 무작위 청약 ID, 답변 커밋먼트다. 커밋먼트에는 답변과 비공개 임의값을 포함한다. 원장 도메인은 네트워크와 컨트랙트를 구분한다. 청약 ID는 판매사·상품·금액에 연결하고, 접수 후 바꿀 수 없게 한다. 모의 서명 확인도 같은 청약 ID·커밋먼트·설명서 버전에 연결한다.

이 구조는 고정한 답변의 바꿔치기와 다른 청약 건으로의 증명 재사용을 검사한다. 고객의 실제 이해나 최초 답변의 사실성까지 보장하지는 않는다. MVP는 서버에서 증명을 생성하므로 서버는 가상 답변을 볼 수 있다.

시연에는 기존 Sepolia를 쓴다. 판매사 A·B, 발행사, 모의 계좌 연동 주체에 별도 테스트 키를 준다. 투자자는 지갑 없이 웹을 사용한다. 거래 서명 키는 서버에서 관리한다. 모든 데이터는 가상으로 만든다. 공개 체인에는 가상 청약 금액과 처리 시점이 드러날 수 있다. 실제 운영망과 거래 정보의 공개 범위는 참여 기관과 별도로 정한다. ZKP를 쓴다고 거래 메타데이터까지 숨겨지는 것은 아니다.

| 기관별 연간 사용료 | 공동 청약 처리, 업무 화면, 검증 이력, 운영 지원 | 기관 단위 계약과 포함 처리량 |
| 추가 모듈 비용 | 상품군·판매 채널·발행사 연결 확대와 규칙 유지보수 | 추가 모듈과 지원 범위 |

투자자의 청약 금액에서 수수료를 나누는 모델은 현재 기본 BM에 포함하지 않는다. 기관의 시스템 연동과 운영에 대가를 받는다. 첫 계약은 한 상품·한 판매 채널의 유료 파일럿으로 가정한다. 기관 간 대조 시간, 수기 재입력 건수, 예외 처리 시간을 기존 방식과 비교한다. 공통 API와 업무 흐름을 다음 고객사에 재사용해 구축 범위를 줄인다. 가격과 지불 의향은 아직 검증하지 않았다.

## 기말 MVP 범위

- 가상 ELS 한 상품, 발행사 한 곳, 판매 증권사 A·B, 읽기 전용 검증자 역할을 만든다.
- 모집 한도는 1,000만원이다. 청약 단위는 100만원이다. 진단 규칙 v1과 설명서 한 버전을 쓴다.
- 고객 세 명의 접수와 한 명의 취소를 시연한다. 서명 누락 요청도 별도로 시도한다.
- 마감 뒤 유효 청약 금액에 비례해 배정한다. 데모 수치는 나머지 금액이 생기지 않게 고정한다. 실서비스의 단수 처리 규칙은 후속 범위다.
- ZKP 생성·검증과 Sepolia 거래는 실제로 실행한다. 계좌의 자금 확보·납입·반환은 모의 처리로 표시한다.
- 한 Vercel 웹사이트에서 사용자·관리자 사이드 탭을 제공한다. 관리자 화면에서 판매사 A·B, 발행사, 검증자 역할을 바꿔 본다.
- 실제 본인인증·전자서명·결제, 만기 상환, 해외 기관 연결, 여러 상품군과 국가별 규칙은 후속 범위다.

청약 상태는 `접수 준비 → 접수 완료 → 배정 완료 → 처리 완료`로 구분한다. 허용 기간에는 `접수 완료 → 취소 완료`로 전환할 수 있다. 접수 거절 건은 배정 대상에 포함하지 않는다. 모의 납입 확인을 받기 전에는 `처리 완료`로 표시하지 않는다. 상품의 모집 상태와 자금 확보·반환 상태는 청약 상태와 별도로 표시한다.

## 기말 MVP 시연 시나리오

| 순서 | 발표자가 하는 일 | 확인할 결과 |
| --- | --- | --- |
| 1. 상품 열기 | 발행사 화면에서 모집 한도 1,000만원, 청약 기간, 설명서·규칙 버전을 등록한다. | 두 판매사가 같은 상품 ID와 조건을 확인한다. |
| 2. 정상 접수 | 판매사 A의 고객 가가 800만원을 청약한다. 진단·위험 확인·모의 서명을 진행한다. | 모의 자금 확보 뒤 실제 ZKP를 생성한다. 컨트랙트가 조건을 확인하면 접수한다. 발행사도 같은 접수 건을 본다. |
| 3. 조건 누락 | 유효한 증명을 쓰되 모의 서명 확인을 누락한 별도 요청을 제출한다. | 컨트랙트가 거절한다. 유효 청약 금액에 반영하지 않는다. |
| 4. 다른 판매사와 취소 | 판매사 B에서 고객 나가 800만원, 고객 다가 200만원을 접수한다. 고객 다는 모집 중 취소한다. | 취소를 기록하고 모의 자금 반환을 확인한다. 유효 청약 합계는 1,600만원이다. |
| 5. 마감과 배정 | 설정한 마감 시각 이후 발행사가 모집을 마감하고 배정을 실행한다. | 고객 가·나에게 각 500만원을 배정한다. 고객 다는 배정에서 제외한다. 배정 합계는 1,000만원이다. |
| 6. 계좌 결과 확인 | 모의 계좌 시스템이 가·나의 500만원 납입과 각 300만원 반환을 확인한다. | 계좌 결과를 받은 뒤 처리 완료를 표시한다. 취소 고객 다의 200만원 반환도 별도로 확인한다. |
| 7. 독립 검증 | 검증자 화면에서 같은 상품·청약 ID를 RPC로 조회한다. 중복 접수와 마감 후 취소도 시도한다. | 판매사 API 없이 원장 상태와 이벤트를 대조한다. 금지한 요청을 거절하고 접수·배정 합계가 유지된다. |

시연 직전에 새 상품과 청약 기간을 설정한다. 마감 단계에서는 실제로 설정한 시각이 지나야 한다. 같은 코드로 Anvil 리허설도 준비한다. 처리 로그는 증명 생성, API 처리, 거래 제출, 거래 영수증, 컨트랙트 이벤트를 구분한다. 거래 영수증이 없으면 대기로 표시한다. 고객 답변·총점·비공개 임의값은 로그에 남기지 않는다.

## 완료 기준

| 입력 또는 상황 | 기대 결과 |
| --- | --- |
| 정상 진단·위험 확인·모의 서명·모의 자금 확보 | 접수한다. 판매사와 발행사 화면의 청약 ID와 상태가 일치한다. |
| 진단 점수 미달 또는 위험 확인 오답 | 고정한 답변으로 유효한 증명을 만들 수 없다. |
| 고정한 답변 변경 또는 다른 청약 건의 증명 재사용 | 원장이 거절한다. |
| 서명 확인 누락 또는 다른 설명서 버전 | 접수를 거절한다. |
| 동일 요청 반복 | 접수 건수와 유효 청약 금액이 중복 증가하지 않는다. |
| 모의 자금 확보 뒤 거래 대기·실패 | 접수 완료로 표시하지 않는다. 원장 결과를 대조해 확보 유지 또는 반환을 처리한다. |
| 취소와 마감 요청 경합 | 온체인 시각·실행 순서·권한으로 전환을 결정한다. 취소 완료 건은 배정에서 제외한다. |
| 고정한 배정 시나리오 | 가·나에게 각 500만원을 배정한다. 배정 합계는 모집 한도 1,000만원과 같다. |
| 모의 계좌 응답 지연 또는 중복 | 확인 전에는 배정 완료 상태를 유지한다. 같은 납입·반환 결과를 중복 반영하지 않는다. |
| 독립 조회 | 미리 설정한 네트워크·컨트랙트 주소를 기준으로 판매사 API 없이 확인한다. |
| 거래 입력·이벤트·상태 점검 | 고객 답변·총점·비공개 임의값·실제 개인정보가 포함되지 않는다. |

## 선행 사례와 현재 상태

[BIS Project Mandala](https://www.bis.org/project/mandala) · [iCapital 발표](https://icapital.com/newsroom/press-releases/icapital-deploys-distributed-ledger-technology-to-streamline-alternative-investment-onboarding-and-pre-trade-processing/)
